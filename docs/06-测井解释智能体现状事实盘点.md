## 2. 当前真实调用链

### 2.1 带附件的首次解释

当前 AgentScope Web 的上传请求并不是先交给大模型判断。

实际链路：

```text
用户：上传井资料 + “帮我解释这口井”
        ↓
UploadInterpretationReply Middleware
        ↓
解析 / 校验上传内容
        ↓
直接构造 run_well_interpretation ToolCall
        ↓
TaskCommandRunner
        ↓
InterpretationTaskService
        ↓
（Task 11 Web）StageOrchestrator 分阶段执行
        ↓
InterpretationWorkflow / W01～W10
        ↓
内部专业 Tool / ModelGateway
        ↓
阶段结果 / 报告 / Execution
```

代码证据：
- `src/cnlc_agent/demo/upload_reply.py`
- `src/cnlc_agent/demo/tools.py`
- `src/cnlc_agent/demo/task_tools.py`
- `src/cnlc_agent/application/service.py`
- `src/cnlc_agent/application/stage_orchestrator.py`

**事实结论：首次上传完整解释当前采用确定性附件路由，绕过了外层 ReAct 模型的 Tool 选择。**

这能够保证上传入口稳定，但它不是“Agent 根据 Prompt / Skill 动态决定是否启动完整解释”的证据。

### 2.2 已有任务的纯文本操作

```text
用户自然语言
        ↓
LoggingInterpretationDemoAgent（AgentScope Agent / ReAct）
        ↓
qwen-plus（正式模式）或 MockTaskShellModel（离线联调）
        ↓
仅两个 Agent-level Tool
        ├─ run_well_interpretation
        └─ interpret_interpretation_operation
                    ↓
        OperationInteractionController
                    ↓
Context / Reference / Scope Resolver
PlanValidator
OperationExecutionBridge
                    ↓
TaskCommands
DependencyResolver
InterpretationTaskService
                    ↓
W01～W10 / 四阶段 / 专业 Tool
```

代码证据：
- `src/cnlc_agent/demo/demo_agent.py`
- `src/cnlc_agent/demo/operation_tool.py`
- `src/cnlc_agent/demo/operation_interaction.py`
- `src/cnlc_agent/demo/operation_execution_bridge.py`
- `src/cnlc_agent/application/commands.py`
- `src/cnlc_agent/application/planning.py`

**事实结论：当前外层 Agent 的确使用 AgentScope ReAct，但模型只负责形成有限的高层 Operation 请求；任务引用、范围解析、计划校验、执行转换及真正的业务执行大量由自定义服务器代码完成。**

## 4. “三个 Agent”与 AgentScope Agent 的实际关系

现有项目文档与 `AGENTS.md` 把以下三个类称为核心 Agent：

- `MainAgent`
- `InterpretationAgent`
- `ValidationAgent`

但代码事实如下。

### 4.1 MainAgent

文件：`src/cnlc_agent/agents/main_agent.py`

它是普通 Python 类，并非 `agentscope.agent.Agent` 子类。

当前职责：

```text
MainAgent.run()
    ↓
InterpretationWorkflow.run(...)
```

代码注释直接描述为：

> “任务级编排入口：启动固定 Workflow”

因此它当前不是一个通过 AgentScope ReAct 动态选择专业 Tool 的 Agent。

### 4.2 InterpretationAgent

文件：`src/cnlc_agent/agents/interpretation_agent.py`

同样是普通 Python 类。

主要用于 W06/W07 相关专业综合：
- W06 fluid 时先通过受控 Tool 获取 Sw；
- 再调用统一 `ModelGateway`；
- 返回结构化 `StageResult`。

它没有 AgentScope Toolkit / Skill / ReAct 生命周期。

### 4.3 ValidationAgent

文件：`src/cnlc_agent/agents/validation_agent.py`

也是普通 Python 类，主要封装模型网关并校验为 `ValidationResult`。

### 4.4 真正的 AgentScope Agent

真正继承 AgentScope `Agent` 的是：

```text
LoggingInterpretationDemoAgent
```

它位于 Demo / Web 交互层。

**事实结论：现有“三 Agent 架构”更多是项目内部职责命名，并不等于三个 AgentScope Agent。**

## 5. W01～W10 当前仍是固定确定性 Workflow

文件：
- `src/cnlc_agent/workflows/interpretation_workflow.py`
- `src/cnlc_agent/workflows/steps.py`

`InterpretationWorkflow` 构造时强制要求：

```text
[node.step_id for node in nodes] == list(StepId)
```

否则抛出 `INVALID_STEP_ORDER`。

W01～W10 当前固定对应：

| Step | 当前代码职责 |
|---|---|
| W01 | 加载 / 解编井资料 |
| W02 | 资料完整性检查 |
| W03 | 曲线质量检查 / 预处理投影 |
| W04 | 岩性识别 |
| W05 | 储层物性评价 |
| W06 | 流体 / Sw |
| W07 | 油气水层分类 |
| W08 | 层段整理 |
| W09 | 综合验证 |
| W10 | 最终结构一致性检查 / provider projection |

专业 Tool / Agent 的调用位置由 `build_steps()` 确定。

**事实结论：专业主流程当前仍然是程序定义的固定步骤链；AgentScope 外层 Agent 不决定 W01～W10 顺序，也不能直接选择这些内部专业 Tool。**

### 8.2 MockTaskShellModel

`MockTaskShellModel` 是确定性本地测试桩。

其 `_command()` 中包含大量正则和关键词逻辑，例如：
- 孔隙度 / POR → POROSITY；
- “全部重跑” → FULL_RERUN；

- “确认 / 继续” → CONFIRM_STAGE；
- 层号解析；
- 百分比转换等。

代码注释也明确说明：它不是生产 IntentClassifier。

**事实结论：使用 MockTaskShellModel 的离线测试只能证明 AgentScope Tool / Schema / Session / Middleware 链路，不是自然语言模型能力的证据。**

**注意：这是“当前程序采用的依赖事实表”，不是本轮已经证明正确的专业测井依赖。**

## 16. 现状与“AgentScope 配置优先”目标的核心差异

### 当前系统更接近

```text
AgentScope Web / ReAct 对话外壳
        ↓
2 个高层任务 Tool
        ↓
自定义 Operation 语义 / Resolver / Validator / Bridge
        ↓
自定义确定性 Task / Stage 编排
        ↓
固定 W01～W10 Workflow
        ↓
内部专业 Tool / ModelGateway
```

### 新设计希望验证

```text
AgentScope Agent
+ Prompt
+ Skill（按需）
+ Toolkit（真实业务 Tool）
+ 原生上下文 / Plan / HITL / Trace（适用时）
        ↓
由 AgentScope 承担更多“理解、选择、计划、调整”能力
        ↓
确定性代码只保留真正不能错的专业与数据安全边界
```

两者不是简单的“旧架构错误 / 新架构正确”。

当前架构的优势是安全和行为确定；代价是自定义交互 / 计划代码非常多，且还没有验证 AgentScope 原生能力是否可以承担其中一部分。

**Task 01 只记录这一差异，不决定删除哪些代码。**

## 19. Task 01 当前结论

目前已经可以回答一部分“现状事实”：

### 已经明确

1. **项目已经真实接入 AgentScope 2.0.8**，并使用 Agent、ReAct、Toolkit、Middleware、AgentState、Agent Service、RedisStorage、事件流。
2. **Skill / MCP 当前被显式禁止**，所以不能说 Skill 已验证无用或可用。
3. **外层正式 ReAct 只有两个高层 Tool**，专业 Tool 不由 Agent 直接动态选择。
4. **首次带附件解释绕过模型 ReAct**，由 Middleware 确定性调用解释 Tool。
5. **W01～W10 是固定程序 Workflow**，MainAgent 不动态规划这些步骤。
6. **四阶段确认能力在 Task 11 已经实现**，但主要由自定义 StageOrchestrator / Repository / API 完成。
7. **自定义 Operation 语义层较重**，大量用户操作解析、引用解析、计划校验和执行转换都已代码化。
8. **版本、权限、任务、Tool 审计、外部 API、Artifact 等确定性基础已经相对完整，具备较高复用价值。**
9. **当前只支持整井参数 Override，不支持层段级参数修改和局部重解释。**
10. **通用查询、Compare、独立重生成报告、通用 Pause/Resume 等尚未达到新需求。**
11. **真实公司能力目前并未覆盖完整四阶段专业处理。**
12. **仓库有大量测试，但本轮没有实际执行测试，且未发现对应 audit commit 的 CI 运行证据。**
